## Journey

A dealer types a stock check with a type word beside the code ("TAP SRTWT5608 x 5", "WC SRTWC8066-SS", "paip SRTWT5608 ada stok?"). After: the parser puts the bare code in `canonical_code` (raw unchanged), the chatbot sends that code to the shared resolver, and the stock reply names SRTWT5608. If the parser did not split (the prompt not yet promoted, or a new shape), the shared resolver asks the parser model one narrow question about the typed text and retries with the code it read out, or offers the code family it read as the existing picker, or says the existing not-found line. The same happens for an API-key `POST /resolve` that sends the typed text (`raw_tokens`), because the fallback lives in the one shared route; `GET /resolve` carries no typed text, so it is never asked (the trace says `no_typed_text`).

## What was built

1. **Parser prompt** (`CANONICAL_CODE_ADDENDUM`, stacked between LOW_STOCK_FILTERS and MEMORY): for hint "product", `canonical_code` is the code alone copied exactly as typed, every other word left out, `raw` the whole phrase; the word beside the code is not a category entity; a bare code carries its own code; never invent, complete, join or correct. Published unlabelled by `alembic/versions/chatbot_canonical_code.py` (down_revision `aig_0001_chatbot_allowed`); the owner promotes by moving the label (or edits prod by hand). Eval: `tests/chatbot/console_cases/2026-10-06-canonical-code-type-word.yaml` through `tests/chatbot/test_canonical_code_live_parser.py` (live, opt-in; also runnable through `scripts/chatbot_console_check.py --prompt-version`): 8 target cases 0/3 on the current text, 3/3 with the addendum; 2 controls 3/3 on both. Budget pin re-measured: 45,757 without the memory addendum, 46,273 whole, `CEILING = 45_761`.
2. **Canonical first in the chatbot**: the sites above read `canonical_code or raw`; the typed raw stays the word the reply quotes (`turn_runtime._typed_by_token` is the one join builder for the three maps). `resolve_entity_body` sends `raw_tokens` (positionally parallel; the route's existing contract), so the shared reader sees "TAP SRTWT5608" and not only the folded token.
3. **Semantic fallback in the shared resolver** (`app/services/resolver_code_reader.py` + `resolve_references(code_reader=)`): after every deterministic tier and before the embedding tier, a pre-extracted product-typed token still matchless is put to the reader with its typed text. `code` re-runs the exact product probe (a hit is `match_tier` "exact", so the gate treats it as the typed code); `family` runs the prefix-then-substring product probe (one row is that code, several flag `ambiguous`, the picker the gate already prints); `none` leaves the miss. `guard` refuses a value not inside the typed text (letters and digits, case folded), so the model can only read a code out, never fix a typo. The verdict rides the new additive `resolutions[].fallback` key, absent when the reader was not consulted.
4. **Bounds**: one provider call per request covering every missed product token, at most 5 tokens (`not_asked` past that), `BUDGET_SECONDS = 3.0`, one attempt, no retry; `_resolve_input` wraps every caller's reader in `per_request` (cap, per-token memo, never raises), and the route's `fallback_to_all_types` cross-type re-run carries no reader at all (the primary pass is the one ask); any failure is an `error` reading with its reason, the token stays a miss. Usage in `ai_assistant_usage_logs` (`feature resolver_code_reader`) unless `dry_run`. Prompt and model: registry key `resolver_code_reader` (fallback text in `ai_prompt_registry`), provider / model from its own `agent_model` override, else the parser's, else the global assistant config. Recorded through `llm_cassette` like every provider call.
5. **Route**: `ResolveReferenceRequest.semantic_fallback: bool = True` and the same query parameter on `GET /resolve`; `false` builds no reader and the response is byte-identical to before. The reader reads a token's `raw_tokens` entry; a token sent without one (every GET token, a POST caller that omits the list) is not asked and carries `fallback: {asked: false, kind: not_asked, reason: no_typed_text}`.

## Known consequences and follow-ups

- The owner's 15-line message answers 13 codes, not 14: `product_code_family.narrow_code_tokens` (PR #833, the resolve route's pre-step) reads every non-code word of the whole `query` as a variant descriptor, so the other lines' `FRG` / `GM` suffixes narrow the bare `SRTWT5608` to `SRTWT5608-FRG` and the base code's line is lost. Pre-existing on main with a bare line; pinned as a strict xfail (`test_the_owners_fifteen_line_stock_check_reaches_the_tool_with_fourteen_codes`); crew-ask on the PR (a separate small fix: descriptor words from the code's own line only, never narrowing a base code whose variants are typed as their own tokens).
- `guard`'s character whitelist refuses `/ . _`, which `_CODE_RE` accepts in a code; a value can therefore never carry one, and the word-edge rule does not treat them as glued either (the catalogue keeps them significant), so a code holding one could be cut at it ("SRTWC8066" out of "SRTWC8066/SS" would read the base product). Measure on prod before relying on it: `select count(*) from products where product_code ~ '[^0-9A-Za-z -]'`; a non-zero count makes `/ . _` the next glued class.
- The reader block ignores `enable_prefix_fallback`; no caller combines the two today.

- The chatbot now sends `raw_tokens`, so the resolver's existing head-code retry (a leading code word, `_HEAD_CODE_RE`, exact-probed; `match_tier` "head_code") can fire for a chatbot token whose raw has a space and a leading code ("SRTWB8004 BASIN TAP" with canonical_code null). Deterministic existing code; with the prompt promoted the canonical token hits the exact tier first.
- "Every confident product-typed miss" (Q3) is implemented as every product-typed miss the chatbot sends: the shared route cannot see the parser's `confident` flag and the chatbot forwards every product entity regardless of it today. Confirm on the hand test.
- A `family` answer for a bare-number token only reaches the availability-mode picker once #1506 PR-2's ladder (`turn/task.code_or_number`) merges; compact mode has it today.
- `GET /resolve` has no `raw_tokens`, so its reader is built but never called and writes nothing; a POST caller that wants the fallback sends `raw_tokens`.
- A hyphen run between two code characters is inside one code whatever the spaces around it (the catalogue folds `[-\s]+` away), so a caller that sends a whole line as the typed text ("SRTWT5608 - 5 pcs") gets no reading for the code in it: it fails safe as a miss. The chatbot sends the parser entity's raw ("TAP SRTWT5608"), where the quantity has already been read out.
