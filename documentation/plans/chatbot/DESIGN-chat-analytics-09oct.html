0. The short version (read this if nothing else)

  1. What we are building. A way to ask questions of the whole chat history ("which products did dealers ask about most in September?", "what did the bot fail on last week?") and get an answer by texting the bot OR on a CRM Reports screen. Same engine, same numbers, both places.
  2. How. Every customer question becomes one row of facts (when, who, what topic, which products, what the bot did, whether it worked). The rows come from three places: the bot's own trace for recent turns (free, already structured), a one-time AI read-through of older messages (one-off, roughly USD 5 to 15), and a small nightly AI pass that names each question's topic.
  3. Topics are decided by AI against a fixed list we agree once (the "taxonomy": about 40 question types under 10 subjects). No keyword or pattern code anywhere. The list changes only by an explicit new version, so a trend line never shifts because the AI changed its mind.
  4. Questions stay flexible in three steps: (1) the existing report catalogue, extended with a "chat" dataset, answers most questions with exact numbers; (2) combinations of those (two groupings, a comparison of two periods); (3) only if (1) and (2) cannot, a guarded read-only query over curated views, with a time limit, a row cap and no access to raw message text.
  5. Privacy. Analytics answer with counts and labels, never with what a customer typed, never with episode summaries. Contact-level breakdowns need a new grant. Dealers see only their own.
  6. Order of work. Six build lanes, each one showing the owner something usable. First lane: the fact table from traces plus a "Chat overview" screen (about five weeks of traced history, 5 Sep on, is already there). Last lane: the AI assistant folds into the chatbot console.
  7. Honest limits. Before 5 Sep we only have message text, and 19 Aug to 7 Sep is a gap in saved parser output. Every answer prints a coverage line so nobody reads a gap as a trend.

1. Problem statement

1.1 What the owner asked for

"Analyse chat history at scale: most asked products in a period, most common questions, what the bot failed on, trends. The questions must be flexible, like ChatGPT over any data." The WhatsApp chatbot is the engine (one engine, chatbot.turns); answers come back by texting the bot AND on a CRM dashboard. Bot replies count, not only customer messages.

1.2 Why it does not exist yet

  • There is no analytics feature over chat. conversation_analysis appears only as an access_agents label (6 contacts + 1 team) and is read by no code.
  • The AI assistant (ai_assistant_service.py, ReAct loop _run_agent_loop :2300, gpt-4o-mini, 6 iterations / 3 tool calls) has no chat tools and no SQL. It is not the engine we extend.
  • The chatbot already answers report questions through the report engine (lanes/business/report_ask.py -> MCP crm_report_ask -> GET /report-ask -> services/reports/ask.py run_ask :152 -> engine.run_summary :930). But its catalogue is sales only: CATALOGUE (services/reports/ask.py:31) has three bases, all over sales order lines.

2. Measurement model (plain language first)

2.1 The five units, and which question uses which

Unit Definition Use it for
Ask (the atomic row) One distinct question in one inbound message. A message "stock <A> and price <B>?" is 2 asks. "Most asked products", "most common questions"
Turn One chatbot.turns row (live, not test, latest attempt). Bot behaviour: answered / failed / clarified, latency
Episode One conversation_frames row: one topic span. "Resolved?", "asked again?", how long a topic took
Conversation-day One contact x one Malaysia day. Activity counts ("dealers who chatted")
Contact One respond_contacts row. Reach ("how many dealers used the bot")

Rule: every metric names its unit. "Most asked product" counts asks; "failure rate" counts turns; "resolved rate" counts episodes. Printing the unit in the reply ("Asks", "Turns") stops a manager comparing a turn count with an ask count.

2.2 Metric definitions

Asked a product. An ask "asked about product P" when P was:

  1. named and resolved: the engine (or the backfill) resolved the customer's words to P's id (trace understood.entities resolved, or the tool call's product args); or
  2. shown: P appeared in the bot's reply rows (response.reply.result_set) for a question that named a brand, category or partial description; counted separately as "shown", never merged.

Unresolved wording ("that blue one") counts at the level it did resolve to (brand / category) or as "unresolved". It is never matched to a product by string similarity (owner rule: semantics only via the parser or the LLM). Today only 592 of ~9,000 live turns resolved a product code, so section 3.4 adds a resolution pass that reuses the bot's own resolver.

Common question. An ask's topic is one leaf of the taxonomy (section 2.3), assigned by the LLM labeller. "Most common question" = ask count per topic leaf, ranked. A leaf is a question TYPE ("stock availability of a product"), not a sentence; the product is a separate dimension, so "most common question about <brand>" is topic x brand.

Bot outcome per turn (from structured trace fields only; no reading of reply text):

Outcome Rule (structured fields) Counts as failed?
answered lane ran a tool, tool ok, replied.rows_offered > 0 or a number reply no
answered_empty tool ok, zero rows ("none found") no, reported separately (often a demand signal)
clarified branch_kind = clarify_menu, or replied.asking, or a required_ask event no (but see "asked again")
refused_policy access_denied, ai_not_allowed, domain grant refusal (domain_grant event) no: working as designed; reported as "refused"
cannot_do not_supported, out_of_scope yes (capability gap)
missed looked_up.missed set, or a crossdomain block that ended the turn yes
phantom a phantom_answer event (bot claimed a fact without a tool) yes (quality)
technical status = failed (184 turns), any failure stage yes
handover escalation to staff completed no; its own metric
noise low_signal (greetings, "ok", stickers) excluded from ask counts

Failed (turn) = cannot_do + missed + phantom + technical. Failure rate = failed turns / (all turns minus noise). The four reasons stay separate in every breakdown, because "the bot cannot do X" (a product decision) and "the bot broke" (a defect) need different owners.

Asked again (episode-level quality signal): within one episode, the next ask from the contact within 10 minutes has the SAME topic leaf and the same product/brand after a bot reply. Determined from the labels (semantic) and the episode (structural); no text comparison.

Resolved (episode). An episode is resolved when its last bot turn was answered / answered_empty / refused_policy, there was no handover, and the contact did not raise the same topic leaf again within 24 hours. This is a proxy, said as such on the dashboard. A true "was the customer satisfied" needs a signal we do not have (no rating, no sentiment stored).

2.3 Topics: how the taxonomy is built and kept stable

  1. Seed from what the engine already knows: the parser's domains (chatbot_domains, models/chatbot_policy.py:31) and intents. That gives the top level: stock, price, order status, delivery / ETA, promotion, product info, account / statement, sales report, complaint, general.
  2. Discovery (one-off): an LLM reads a stratified sample of ~2,000 masked asks (all eras, all domains) and proposes leaf question-types under each seed subject, with a one-line definition and two INVENTED examples each. Target 30 to 50 leaves; anything rarer than 0.5% of asks folds into <subject>.other.
  3. Owner review: the owner accepts / merges / renames leaves in a short list (a taxonomy_v1.md in this folder plus the seed rows). That review is the only place the list changes.
  4. Frozen version. Every label row records taxonomy_version, model, prompt_version. A trend chart only compares labels of ONE version; re-labelling history to a new version is a batch job (cheap, section 3.6) run once per version bump, so the whole history moves together.
  5. "Other" with a proposal. When no leaf fits, the labeller returns other plus a short proposed leaf name. A monthly report lists the top proposals; promoting one is a v2 bump.

Why not let the LLM invent topics freely each time: counts would not be comparable week to week, and "the most common question" would change because wording changed. A fixed list is what makes a trend a trend.

2.4 How bot replies are classified

  • Live era (5 Sep on): from structure only (the outcome table above), plus what was SHOWN: response.reply.result_set items (products offered), quick_replies (menu offered), attachments_src (catalogue / flyer sent). No LLM needed.
  • Pre-turn era: only reply text exists (chat_histories outgoing, avg 540 chars). The backfill LLM classifies each bot reply into the same outcome set from the reply AND the ask it answered. Where chat_histories.result holds product items (7,217 items, 14 Jun to 22 Sep), "shown" products come from that structure, not from the text.
  • Staff replies (a human in the chat) are a separate reply class staff, never counted as bot answers. Identification: outgoing rows with no chatbot_turn_id (models/chat_history.py, the column added by QUOTED-REPLY R1) during a span when the contact was human-intervened (memory.py contact_is_human_intervened). Coverage of staff replies in chat_histories is unknown (open question Q5).

2.5 Edge rules

Case Rule
Test turns Excluded everywhere: is_test = true (2,171 turns) and ingress = console. A test turn never becomes a fact row.
Retries One fact row per respond message_id: the latest attempt (unique key models/chatbot_turn.py:63).
Duplicate history rows From 14 Aug, chat_histories is unique per message id (CHAT_HISTORY_DEDUPE_CUTOVER). Before that, exact duplicates (same contact, direction, message_id or same text + sent_at to the second) collapse to one. Exact equality only.
Multi-ask turns The labeller splits a message into asks (ask_seq 1..n). Turn measures count the turn once; ask measures count each ask.
Era overlap 5 Sep to 22 Sep both chat_histories structure and traces exist: traces win, history rows for those turns are skipped (joined by chat_histories.chatbot_turn_id or the respond message_id).
Media messages An image / voice note counts as an ask when media extraction produced text (media_intake stage); otherwise outcome noise.
Internal staff contacts Contacts linked to a user (users.respond_contact_id, models/user.py:72) are tagged audience = staff and filterable out of "customer" metrics.

3. Engineering: data pipeline

3.1 The whole flow

Four producers, one fact store. Nothing new sits in the turn's request path except (A), which is a single INSERT at turn close of values the turn already holds.

Volume: ~25,000 ask rows for the whole history today, ~300 to 400 per day. Years of headroom on plain indexes (asked_at, topic_code, contact_id, items by ref_id).

3.3 (A) Trace flattener

  • Where: the engine's tail, after the turn closes, as one more step that never fails the turn (wrapped; a failure is logged and the nightly sweep refills).
  • What: reads only the trace stage records already in memory: understood (intent, domain, entities, message_type, tokens), looked_up (domains, missed, gate_reason, exit, tool {name, args, domain, ms}), replied (rows_offered, asking, cross_domain_block), the kind events (tool, crossdomain, domain_grant, phantom_answer, required_ask), and response.reply.result_set for shown items.
  • Writes ask_seq 1 with topic_code = null; the labeller fills topic and splits further asks.
  • Skips is_test and ingress = console turns entirely.
  • Nightly sweep: INSERT ... ON CONFLICT DO NOTHING for any closed live turn of the last 3 days with no fact row (covers crashes and the first deploy).
  • One-time: run the sweep over every turn since 5 Sep (11,161 rows, seconds).

3.4 (C) Nightly labeller (topic + ask split + product resolution)

  • RQ job on the existing worker (new queue analytics, added to WORKER_QUEUES), scheduled nightly at 02:15 Malaysia by the existing scheduler; also runnable on demand.
  • Input per ask: the customer's message text (read from chatbot.turns.envelope, never stored in facts), the parser's domain/intent/entities, the bot's outcome and the first 300 characters of the bot reply, plus the taxonomy leaves (prompt-cached).
  • Output (strict JSON schema): list of asks {ask_seq, topic_code | "other", proposed_leaf?, product_words[], brand_words[], confidence}.
  • Product resolution: product_words go through the SAME resolver the bot uses for entity words (report_ask._resolve_word :350 path / the head resolver), not a new matcher. A unique hit writes a chat_ask_items row resolved_by = resolver_pass.
  • Model: through the one provider seam (services/llm_provider.py), configured in System Settings like the parser (today gpt-5.4-mini). Batches of 40 asks per call, grouped by contact-day so the model sees the neighbouring asks (that is how it splits "and that one also?").
  • Idempotency: a row is labelled when topic_code IS NULL or its taxonomy_version is older than current; the job picks rows, labels, writes in one transaction per batch.

3.5 (D) One-time backfill for old messages

  • Scope: chat_histories rows before 5 Sep, plus 5 to 22 Sep rows that did NOT come from a turn. Incoming rows become asks; outgoing rows supply the reply each ask got (the next outgoing bot row of the same contact) and staff replies (section 2.4).
  • Same prompt as the labeller, plus "classify the bot reply outcome" (only this era needs it). Era B rows pass the saved parser_raw domain/intent as a hint. Era rows with result items pass those as "shown" items directly (no LLM).
  • Batching: per contact, per day, 40 asks per call; a resumable cursor table (chatbot.chat_backfill_runs: run id, last processed id, counts, cost) so a stop resumes.
  • Idempotency: unique (history_message_id, ask_seq) upsert; re-running is a no-op.

Cost estimate, from real volumes. Customer text is tiny (22,845 incoming messages, ~481 KB, avg 22 chars). The bulk is bot replies (31,050 outgoing, ~16 MB, avg 540 chars), and we send only the first 300 chars of each.

Item Count Tokens per unit Tokens
Pre-turn incoming asks (22,845 total minus ~9,000 live-era) ~13,800 ~10 text + ~25 parser hint/meta ~0.5 M in
The bot reply each ask got (300 chars) ~13,800 ~80 ~1.1 M in
Neighbour context (previous ask of the same day) ~13,800 ~15 ~0.2 M in

At small-model list prices (order of USD 0.4 to 1 per million input tokens, 1.6 to 5 per million output), the whole one-time work is about USD 5 to 15, the nightly job a few US cents per day. The provider's current price page is the authority; the run table records actual spend per run. Runtime: ~350 calls, at 4 concurrent calls about 15 to 30 minutes, well inside the 200K tokens/min limit seen in prod (llm_call.py:6) if paced at one call per second.

3.6 Re-labelling

A taxonomy bump sets current_version; the labeller treats older rows as stale and relabels newest first. Full history relabel ~4 M input tokens, the same order of cost as the backfill. Old labels are overwritten (no history of labels kept: one version is live; the audit sample keeps its own record).

6. Later phase: AI assistant becomes a chatbot console

Today the console (POST /api/v1/system/chatbot/console/turn, console_service.run_console_turn :444) is a dry run that impersonates a contact. The unification: a staff user types into the CRM chat panel, the turn goes in as ingress = crm with the STAFF identity (users.respond_contact_id links a user to a contact, models/user.py:72), runs the same engine and the same grants, and is recorded (not a dry run, but excluded from customer analytics by audience = staff). The ai_assistant_service.py loop is retired once its tools are covered. Separate lane, after analytics is proven, because it touches auth and the engine's ingress contract.

7. Evaluation

  1. Golden question set (~40 questions): each with the expected structured route (dataset, group, measure, filters, period) and the expected answer computed by hand-written SQL over a SYNTHETIC fixture (seeded turns, frames, histories). Pytest asserts parser-route and numbers. Run in CI on every change to the catalogue or prompt; prompt changes also run it against the provider in a nightly job (not in CI).
  2. Label accuracy audit: per taxonomy version, a stratified sample of 300 asks (by subject and by low confidence) relabelled by a larger model, disagreements reviewed by the owner or a delegate in a small review screen. Target: topic agreement >= 90% at subject level, >= 80% at leaf; product resolution precision >= 95% (a wrong product is worse than "unresolved").
  3. Outcome rule tests: one fixture turn per outcome row in section 2.2 (trace JSON in, outcome out). These are pure functions: fast unit tests.
  4. Coverage tests: the coverage line computed on a fixture spanning eras.
  5. Regression: existing report_ask sales tests must stay green (the dataset axis defaults to sales); the reviewer's kill test covers the grant checks.
  6. Reconciliation: nightly check that live-era fact rows = closed non-test turns (by day); mismatch alerts the operator.
