ARCH: a "Claude Code for Sorento" chat advisor (16 Oct 2026)

Status: DRAFT for owner review (lane CHAT-ADVISOR-SPIKE, PR #1711). Design plus a measured spike; nothing here changes the live chatbot. Numbers marked estimate are replaced by measured spike numbers in section 8 by 19 Oct. Code cited at origin/main 504ce9252a.

0. Short answer

Can we build it on the current architecture? Yes, as an added layer, not a rewrite. Of the seven layers, Sorento already has channels (1), a strong understanding step (2), carried state (4, partly), a large tool layer with permissions inside it (6: 52 MCP tools, Stock Visibility enforced in the backend) and traces (7). The one layer that does not exist is 3, reasoning: today code picks exactly one tool per ask and fills a template, so the bot can be correct but cannot think "this is out of stock, the alternative has stock, and there is a promotion on it".

Recommendation (to be confirmed by the spike): option C, the hybrid. Keep the parser and today's fast, templated answers for plain asks. Send only the selling moments (out of stock, a promotion exists, a fitting accessory exists, a quantity or ETA to counter, a project) to an advisor model that may call 3 to 6 tools chosen by the parser's domain, sees one structured conversation state, and whose reply passes a fact guard: every code, number, price and date in the reply must appear in a tool result, or the reply is redone or falls back to today's answer.

"As Claude Code, do you extract entities first?" No. Claude Code reads the raw conversation plus the tool descriptions, and one model understands, decides and calls tools in a loop, looking facts up instead of carrying them in the prompt. That shape is tested in the spike as C2 (the advisor reads the raw transcript, no parser output) and C2-all (C2 with every read-only tool, which is the shape that failed in n8n).

4. Option C in detail

What decides "selling moment"

Not keywords (owner rule: the parser decides meaning). Two triggers, both from data the system already has:

  1. The parser's reading is open-ended or selling (a recommendation ask, "anything else", a counter-offer, a project enquiry), or
  2. the fast-path tool result carries a hook: on-hand below the asked quantity or zero, a stored alternative, a live promotion on the product, a stored fit, an incoming row. Code sees the hook in the result; the advisor composes.

The four parts

  • Tool subset: the parser's domain picks the shelf from the existing chatbot_domains table (inventory, promotion, incoming, master_products, ...; it already maps domain to tools) plus a short companion list (for stock: incoming-by-product, promotion products, find/fits). Never more than 6; write tools never reach the model; contact and space are stamped by code, so permissions stay in the tools.
  • One structured state: the parse of this turn, the carried subject, the open question, the last exchanges. C2 replaces this with the raw transcript.
  • Fact guard: every product code, quantity, price, percentage and date in the reply must appear in a tool result of this turn or in the user's own words; UUIDs are always a leak. One retry naming the bad tokens, then the fast-path reply.
  • Traces: tools called, results, tokens, cost and the guard verdict go into the turn trace, like today.

Three ideas taken from Respond.io's agent (option E)

  1. A knowledge lane for static questions. Specs, fitment, policies, how to order: answered only from static sources (product attachments, user guides), otherwise "I don't know" plus a handoff. It never states a live number; live numbers stay with the tools.
  2. Tool cards instead of a bare tool list. Each tool the advisor may call carries: when it applies, the inputs it needs and how to ask for a missing one (one question at a time), and fixed exits (done / ask / hand over to a human with a summary / cannot answer). The current product and customer live in state slots, not in the chat history.
  3. Code proposes, the model picks and words it (variant C3). Code turns the tool results into 1 to 3 next-best options (in-stock alternative, live promotion, incoming date, matching accessory), each with its sentence already filled from data. The model only chooses one (or none) and writes the words around it; every number stays template-filled, so the fact guard has nothing to catch. Tested in the spike as C3 if time allows.

7. The spike: what we measure

  • Scenarios: 30 real "salesman moments" from dev chat history (alternative, promotion, accessory, quantity counter, ETA counter, project; at least 12 follow-ups, the parser's weak spot) + 10 plain control asks. Names masked in anything committed.
  • Arms: v1 today; C and C2 on claude-sonnet-5-5 and gpt-5.4-mini; C2-all on claude-sonnet-5-5; C2 on claude-opus-5-5 for the follow-ups (does raw context help with a stronger model?); C3 (code proposes, model picks and words) if time allows.
  • Per scenario: right tools, made-up facts (guard + judge), owner-rule compliance (truthful, no ids, Stock Visibility, qty ask in availability mode, clarify not assume, carry quantity), helpfulness (judge rubric), salesman move made, p50/p95 latency, tokens and cost per turn.
  • Bounds: dev DB only, existing MCP tools only, a script (no live path change), about $30 of model spend in total.

9. Production build (draft, refined after the spike)

  • Size: L (new layer, a per-contact switch, a migration for the switch column). Advisor module under app/services/chatbot/advisor/ (loop, subset, guard), called from the turn engine after the fast path.
  • Migration path: off by default; per-contact switch like PV2's (console extra, contact column, dev-only system setting); staff contacts first, then a few dealers; the fast-path reply is always the fallback.
  • Gates: the salesman scenario set + today's eval sets (no regression on plain asks), 0 made-up facts reaching the user, p95 at or under 8 s on advisor turns, daily cost cap, owner hand test.

10. Questions for the owner

  1. Which turns may the advisor take? (a) only selling moments as in section 4 (recommended: keeps plain asks fast and cheap); (b) every product turn; (c) every turn (option D).
  2. How many moves per reply? (a) one (recommended: WhatsApp, short); (b) up to two.
  3. May it mention a live promotion on a plain stock ask? (a) yes, when the promotion covers that product (recommended); (b) only when asked about promotions.
  4. Guard fails twice: (a) send today's template reply (recommended: never worse than today); (b) hand over to a salesperson.
  5. Model: decided from the spike numbers in section 8.
