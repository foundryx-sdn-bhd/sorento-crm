1. P1 Follow-ups lose context

What happens

On crew's parser gold set (real turns, TRAIN slice only), v1 reads 49 and 51 of the 81 follow-ups right in two runs; 29 fail in both. Giving the parser the whole raw chat did not help (59.9% vs 61.8% on all follow-ups), so the fix is not "more history". It is four specific gaps.

Why

  1. The current subject is cut on 77 of 81 follow-ups. It comes from the carried focus (session_state.py:23) through head/parser.py:809-848 and engine.py:4511-4522 into context.assemble. Since #1527 (9 Oct) the same block also carries the brand, product type, product detail and promotion lists (about 629 tokens, context.py:147-158), kept whole (:409-410), against a budget of 350 tokens (:29), so the shrink loop (:425-431) always drops the subject. The builder that the tests cover (parser.py:851-944) is no longer called, so no test saw it.
  2. A question already answered still shows as open (4 items): an old "did you mean" list stays as the open question, so "the NEW one also" picks a list position (question.py:73-93, engine.py:4503, :4523-4524).
  3. Prompt rules pull short replies to "casual" (4 items): "office use copy", "what different", "why?" are read on their own words (prompt v94 lines 313-319), against lines 35-56 that say read them in context.
  4. Product questions read as file requests (6 of the 15 misreads): "SRTSCBD313 seat cover", "size?" and carton questions become a document ask (prompt lines 332-341, 1439-1441).

2. P2 Spec matching

What happens

The owner's chat is newer than the local logs (they stop on 13 Oct), so it was reproduced by running today's code on dev data. "bathtub with massage jet", "massage bathtub" and "whirlpool bathtub" all return the same kind of list: plain tubs (BRBTB25706W-LEFT "simple bathtub", SRTBT1835-16, SRTBT1876-15, ...). None has jets. Dev data holds about 193 right answers (176 Jacuzzi-class products, 16 "Bathtub and Jacuzzi" ones such as BRJC25410W-2 "massage bathtub", and SRTBT1605-12 "air bubble bathtub").

Why

  1. The parser can only name spec keys that exist (head/parser.py:173-179). The spec registry has 52 keys; none is massage, jet, whirlpool or bubble. The feature lives only in the product description text.
  2. An unknown feature is dropped without a word (grounding.py:738-749; only promotion asks say it back). The search then runs on the class alone: "bathtub" means {Bathtub, Bathtub and Jacuzzi} (product_spec_search.py:1103-1141), and in exact mode free words never count (:1411-1424). The Jacuzzi class was split from "bathtub" on purpose (product_class_signal.py:74-81).
  3. Twelve other real spec asks (dev logs): 3 right, 9 wrong. Five pick the wrong size axis ("200mm wc" searched as width; trap length has 51 matches), one lets the parser's colour word beat the registry ("gold" tap, grounding.py:601-618), two are parser misreads of the product (P1 territory), one reads "300mm below" as "exactly 300mm".

3. P3 Report engine

What happens

The live chats on dev hold no report asks, so these 25 come from the human console test sessions (3 to 14 Oct): 7 right with at most one question, 7 right only after 2 or 3 questions, 11 failed; follow-ups 2 of 8 right. The 14 right answers needed 18 questions before any data; 14 of them were "how many", "amount or quantity" or "delivered or ordered".

哪一位经销商卖得最多SRTWC286-SH-NEW
(asks the period, how many, amount or quantity, delivered or ordered)
2026, top 10, by quantity delivered
How many? ...then: Quantity or amount?

Why

  1. Four questions are forced before a ranking runs (lanes/business/report_ask.py:225-243), per the 4 Oct ruling "never default metric or basis" (:8-9). Every row already shows both RM and pieces (presenters.py:3361), and the multi-ask path on the same engine asks only the basis (turn/sub_asks.py:776-784): two policies on one engine.
  2. Answers are not read back: only the field just asked is taken (report_ask.py:183-212, :552-561), so "2026, top 10, by quantity delivered" answers one question and the rest are asked again; "3" is "not a number". Top selling already reads these reliably (engine.py:2568-2591). "delivered" also switches the report type and returns the delivery-order list (:242, turn_runtime.py:1894-1897).
  3. The report is lost on follow-ups: the multi-ask never stores it (sub_asks.py:776-800); it is carried on one reading type only (turn_runtime.py:1950-1956); a refine re-sends the same table (report_ask.py:658-686); a new axis drops the period (:633-637).
  4. Shapes not covered: "how many dealers sell X" gets a top-10 list though the count exists (reports/ask.py:291); a dealer's brand filter is dropped silently (__init__.py:2026-2030). Plus a 10-per-10-minutes limit that counts every refine, and display issues (duplicate brand names, category codes, ISO dates, header not naming the sort).

5. Decisions for the owner

Open: 1 and 2. No fix lane starts until they are answered.

  1. Report defaults (P3-F2). The 4 Oct ruling says never default amount/quantity or delivered/ordered. (a) Keep it: 3-4 questions before a ranking. (b) Default to amount and delivered, ask only the period, show the choice in the header so "by quantity" or "ordered" re-runs it (recommended: removes 14 of 18 questions; quantity and amount are both shown on every row anyway).
  2. Should "bathtub" also list jacuzzis? (a) No, keep the split; jetted tubs come back only when a massage or whirlpool word is used (P2-F1) (recommended). (b) Yes, "bathtub" always includes jacuzzis (adds 151, reverses the split made on purpose).
  3. Prompt changes (P1-F2, P1-F4) need a new parser prompt version on the live bot. Answered 16 Oct (crew): yes, each prompt fix ships as its own prompt version behind the parser gold gate (the main chatbot gate, owner 15 Oct), and each still needs the owner's hand test before merge.

6. What was dropped

The 15 Oct "advisor" idea (a reasoning model writing free-form replies over the tools) was stopped on 16 Oct after two smoke runs, $2.08 of model spend. Two facts from it still matter: (1) staff and walk-in customers never see stored alternatives, because the detailed stock view returns before alternatives are attached (inventory_service.py:1439 vs :1480); only dealers get them. (2) A model-written reply needs a fact guard and still slipped on "not on record" claims it never looked up: one more reason to keep structured replies.
