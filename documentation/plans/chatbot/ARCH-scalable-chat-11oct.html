Scalable chat architecture: review

AGENT-LOOP-SPIKE design lane, 11 Oct 2026. Reads code on branch base 43b11a99a and the 107 DEV eval cases (customer names masked). No live LLM calls were made. Every figure marked est. is an estimate to be measured on the eval set before any switch.

Summary1. TodayWhere it is rigid2. Crew proposalMCP-only variant What the market does3. Counter-proposalsWhere controls live4. Chats walked through5. Numbers6. Recommendation
Recommendation (short). Keep the parser as a router and MCP as the only execution layer. Change three things, area by area, gated on the hidden eval:
  1. Prompt diet first: a small core prompt plus only the cards for the areas this message touches, plus 3 to 5 retrieved worked examples. This replaces the one 37k-token static prompt. Tokens drop by about 65% (est.) and it needs no tool change.
  2. The parser emits the MCP call itself: tool plus typed params taken from the MCP catalogue, instead of 54 hand-written schema keys and per-area transform code. Follow-ups patch the held call. Today already does exactly this for one area: the sales ranking frame.
  3. The conversation layer is keyed by param type, not by domain: a product_ids param brings the resolver, did-you-mean, picker and stamps with it, and a customer_ids param brings the customer roster and scope. A new area is then a new MCP tool with typed params plus an area card and examples, with no new chatbot code.
To the owner's challenge "this looks like what we have": yes, about 70% is the same, and that is on purpose because what works stays. Only the three items above are new. Without them it is a rename (see section 2).

1. Today's architecture (from the code)

LLM callrigid pointMCP / backenddeterministic code
Measured. Code fallback prompt 148,593 chars (about 37.1k tokens). Prod snapshot of 1 Oct 132,040 chars (33.0k). Candidate of 10 Oct 152,918 chars (38.2k) plus DB policy blocks. The JSON schema sent on each call is 7,329 chars. The per-turn user block is capped at about 1.8k tokens (turn/context.py:29). Total is about 37k to 42k tokens a turn, which matches the owner's 39k. Almost all of it is the static system prompt. A typical business turn makes 1 LLM call (eng :4513). It can make up to 3: resolver code reader resolver_code_reader.py:49, spec read references.py:3588, clarifier casual.py:296. Business reply text is all templates. Baseline: p50 3.9 s, p95 7.9 s, about $0.010 per case (98% of prompt tokens cached).

Where it becomes rigid

R1. One prompt for everything. Every new kind of question adds an addendum: the report and ranking addenda alone are about 33k chars (about 8k tokens). All of it is sent on every turn, even "SRT359C stock". Rules start competing with each other (cases 0185, 0258 below).
R2. Hand-written parser keys per area. 54 required keys (parser.py:84-578), such as ranking_refine, ranking_drill, top_n, order_status, low_stock, po_refs. Each must then be translated into tool args by area code (fetch.py:650, report_ask.py:564).
R3. One tool per domain. select_tool takes tools[0] of the domain row (fetch.py:156). A second question shape in the same domain needs a new domain or new special-case code.
R4. Follow-ups exist for one area only. "Shrink it down" works for sales ranking because Focus.sales_ranking_frame holds the last call (state.py:176, report_ask.py:641/710). Other areas carry a subject (product, customer), not the last call, so they carry the wrong thing or ask again (cases p9ob, 0228).
R5. Missing filters live nowhere. No MCP tool has a spec-attribute filter or a "has active promotion" filter today. include_specs only adds output columns (catalog.py:94). So "exposed shower that has stock" or "which basins are on promo" cannot be one query (case 0277).
R6. Compound asks fall into required-field loops. "Stock + DO for two months + ETA" in one message triggers "how many units?" from required_fields.py and drops the DO half (case 0058).

Answering "that looks pretty similar to what we have today", head on. It is. Today's parser already turns a message into structured parameters, and today's sales ranking already keeps the last call and patches it. As written, the proposal is a refactor that generalises two existing mechanisms. It becomes more than a rename only if (a) the prompt stops being one static 37k block, (b) the emitted params are the tool's own typed params so no per-area translation code is written, and (c) the picker, did-you-mean and stamps trigger from the param type instead of from domain code. Its weak point is the executor: a raw query layer would have to re-implement five layers of per-mode control that MCP and the routes already own. So it should not bypass MCP. That leads to the variant below.

Owner/crew variant: MCP stays the only execution layer

Pros. Every control that works today keeps working: did-you-mean alternatives (inventory_service.py:1147), presenters per mode (presenters.py:1831), dealer ETA padding (eta_policy.py:400), customer scope (_contact_scope.py:32). The model chooses among 2 to 5 tools, not 44, which avoids the n8n failure and is within OpenAI's under-20 tools guidance. "Shrink down" becomes uniform.
Cons. Two sequential model calls on most business turns, so p95 sits close to the 8 s bar (est. 6.5 to 8.5 s). The tools are still shaped per area (orders list, outstanding, sales report, top selling and report ask are five report tools with overlapping params), so the filler still has to pick within an overlapping set. Market warning: "if a human can't say which tool, the agent can't".

3. Options compared (including counter-proposals)

Five options. A and B are crew's. C is the market set (1)+(2)+(5)+(6)+(7) that crew asked to evaluate. D and E are mine. D is the recommendation and is built on top of C.

A. Datasets + generic executor (crew, as written)

Markets: 3, 5. See section 2. Rejected as written: it bypasses MCP controls.

B. MCP-only, router + param filler (owner/crew variant)

Markets: 1, 5, partly 2. Two model calls. See above.

C. Market pattern set (1)+(2)+(5)+(6)+(7), evaluated as one option

Pros. One LLM call (the router and param filler fused into one call, with the routing done cheaply by retrieval), so it is the fastest option with tools. The prompt diet comes for free. Consolidating the 5 overlapping report tools into one report tool removes the hardest "which tool" choice. Refinement is uniform.
Cons. If retrieval picks the wrong areas, the card is missing and the model has to say "area not loaded", which costs a second call (est. under 10% of turns, UNVERIFIED). Building report, product_search and promo_match is backend work: the spec and promo filters are new. The conversation layer stays domain-coded, so a new area still needs chatbot code for its pickers and stamps.

D. (mine, recommended) C + a param-type conversation layer

Pros. This is what removes "every new kind of question needs a new tool + new domain + new code". Today the conversation layer is wired per domain: stamp_promotion/stamp_purchase_order flags (eng :5202-5227), the customer has-DO annotator (pickers.py:82), and required_fields.py. In D it is wired per param type, declared once. It fixes R6: quantity is asked only when the chosen tool marks it as required, so "stock + DO + ETA" never asks for quantity for the DO half. It keeps MCP and today's templates.
Cons. The foundation is the largest build here (est. 3 to 5 weeks before the first area moves). The registry must reproduce today's special cases (the dealer did-you-mean without escalation, dealer_stock.py:77; the tier picker with stamps, eng :5824). Every special case needs a red test from today's corpus before it moves.

E. (mine, conservative) Prompt diet only, on today's pipeline

Keep the 54-key parser and everything behind it. Replace the static prompt with core + addenda for retrieved areas + 3 to 5 retrieved examples (patterns 6 and 7 only). Pros: 1 to 2 weeks, low risk, est. 60 to 70% fewer prompt tokens and a faster parser call. It is also step 1 of C and D, so the work is not lost. Cons: it does not fix R2 to R6. Every new area still costs a new addendum, new schema keys and new lane code. It is a diet, not a scaling fix.
Not recommended: the free tool-calling agent (the first half of this lane). The owner saw a model choosing from many tools pick wrong tools and get slower in n8n. The market agrees: pattern 1, with free loops only as a bounded fallback (pattern 8). The red tests and plan from that spike were removed from this branch.

6. Recommendation and questions

Do D, in this order, each step behind the hidden eval gate (per topic, p95, tokens):
  1. Step 1, E (1 to 2 weeks): core prompt + per-area cards + 3 to 5 retrieved examples on today's parser. This is the prompt diet, at the lowest risk, and it gives real latency and token numbers to plan the rest on.
  2. Step 2, reports first (C): the parser emits report_ask params directly, the 5 report tools merge behind one report MCP tool, and the held call plus patch is generalised from sales_ranking_frame. This removes the largest addenda (about 8k tokens) and the most rigid area.
  3. Step 3, product_search and promo_match: add spec_constraints and has_active_promotion to MCP (backend routes, declared restricted_fields). This covers spec match, promo match and scenario asks.
  4. Step 4, param-type registry (D): move did-you-mean, picker, stamps and the quantity ask from domain branches to param types, one area at a time, each with red tests from today's corpus.
  5. Lookups (stock, ETA, SO status) move last, and only once each matches today on the eval. A bounded fallback loop (pattern 8) only after that, if the eval still shows compound misses.
Honest expectation: today is at 78% and the switch bar is 95%. Steps 1 and 2 should move cost and p95 measurably. Whether 95% is reachable is not knowable from code reading; the eval after step 2 is the first real signal.

Questions for the owner (at most 5)

  1. MCP as the only execution layer: confirm, and rule out a raw query or SQL executor (option A as written)? Recommendation: yes. MCP and the routes own five layers of per-mode control.
  2. Start with the prompt diet (E) as its own step before any tool change? Recommendation: yes. It is low risk, measurable within a week, and needed by every option.
  3. First area to restructure: reports, or product search with spec and promo match? Recommendation: reports. A held-call refine already exists there, the addenda are the largest, and the 5 tools overlap the most.
  4. OK to add two new MCP filter params (spec_constraints on product search, has_active_promotion) as backend work inside the area lanes? Recommendation: yes. No option answers spec or promo match without them.
  5. Gate per step: a step ships only if no topic gets worse on the hidden eval and p95 stays at or under 8 s; the 95% bar applies to the final switch? Recommendation: yes. It keeps "never regress what works" testable.
