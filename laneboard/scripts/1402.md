# Hand test: PR #1402 CHAT-LOCAL-FIRST (thread reads local first; Respond.io for delta sync and backfill)

## URL

crew test copy

## Setup

1. Apply the lane's additive DDL to the copy's database (the crew-migration SQL on the PR: five
   `chat_histories` columns, `chat_thread_sync_state` with `newest_synced_message_id`, the
   `chat_history_reconcile` scheduled task row).
2. Backend AND worker running, `ENABLE_SCHEDULER=true` on the worker so the reconcile task ticks
   (every 5 min) and the worker drains the `respond_io` queue it enqueues on.
3. Egress to `api.respond.io` ALLOWED for steps 1 to 9 (read-only message lists), BLOCKED by crew
   from step 10 on. Step 7 and step 9 send real WhatsApp messages: crew's go is required before them.
4. A portal login for a contact linked to a sales agent with the `conversation` switch on, whose
   customers have WhatsApp history (the lane SALES-CONVO account).
5. A CRM login holding `system.chat_history.view` and `sla_management.conversations.view`, with at
   least one open intervention ticket assigned to it (the ticket panel steps). The Respond.io call
   counter is read from that tab's devtools console:
   `fetch('/api/auth/token').then(r=>r.json()).then(t=>fetch('/api/v1/system/chat-history/respond-io-calls?minutes=3',{headers:{Authorization:'Bearer '+t.token}})).then(r=>r.json()).then(console.log)`

## Steps

1. CRM tab: run the counter snippet, note `total`.
2. Portal: open Conversation, pick a customer with existing history, note how long the thread takes.
3. CRM tab: run the counter snippet again.
4. Leave the portal thread open 60 seconds, run the counter snippet again.
5. Portal: scroll the thread to the top repeatedly until it stops loading older messages; run the
   counter snippet again.
6. CRM: Dashboards > My pending tasks > open an intervention ticket; the conversation panel opens.
   Run the counter snippet.
7. In the ticket panel, type a reply and send it (crew go). Watch the panel.
8. Leave the panel open 60 seconds; run the counter snippet.
9. From the phone, as that ticket's contact, send one WhatsApp message (crew go). Watch the panel
   and the portal thread for up to 5 minutes.
10. Crew blocks egress to `api.respond.io`. Refresh the ticket panel and the portal thread; open two
    other customers' threads in the portal.
11. CRM: System > Scheduled tasks > "Chat history reconcile" > Run now; read its run summary and the
    worker log line starting `chat reconcile:`.
12. CRM: SLA > Conversations, open the same customer as step 2, scroll the thread.

## Expected

1. A number N.
2. The thread renders immediately from stored history (under 1 second, no wait on Respond.io).
3. `total` is N or N + 1 (one delta read queued after the open). Never more.
4. Unchanged from step 3: the six polls made 0 Respond.io calls.
5. Grew by at most 1 per scroll-back past the stored history; 0 for scroll-backs inside it; stops
   asking at the conversation start.
6. The panel renders the thread immediately; `total` grew by at most 1 (the one delta read).
7. The sent message appears in the panel within a second of the send (from `chat_histories`, the
   CRM's own mirror row), with a sent tick; no Respond.io read is needed for it.
8. `total` unchanged from step 7: the panel's polls made 0 Respond.io calls.
9. The message appears in the panel and the portal thread within seconds (n8n or the Respond.io
   webhook), and in any case within 5 minutes (reconcile); the polls still add 0 calls.
10. Every thread and the panel render from stored history exactly as before; no error, no empty
    thread; the counter grows by at most 1 per thread opened (a failed delta read that then backs
    off), never per poll.
11. Run summary `{"enqueued": "<job id>", "queue": "respond_io"}` within seconds; worker log line
    like `chat reconcile: {'selected': <n>, 'synced': <n>, 'errors': <n>, ...}`; no crash.
12. Same messages as the portal shows; a previously sent image or PDF renders as an attachment
    bubble with its file name, not as a text placeholder.
