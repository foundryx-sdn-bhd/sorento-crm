## Steps

Part A, offline:

1. CRM tab: run the counter snippet and note the number N.
2. CRM: Dashboards > My pending tasks > click the ticket. The conversation panel opens.
3. Run the counter snippet.
4. Leave the panel open for 60 seconds, then run the counter snippet again.
5. In the panel, scroll the thread to the top until no older messages load. Run the counter snippet.
6. Set the browser width to 375 px (devtools device toolbar) and look at the panel.
7. Portal: open Conversation, pick a customer that has stored history, and leave it open for 60 seconds.
8. Run the counter snippet.

## Expected

1. A number N.
2. The thread renders immediately from stored history: the newest 50 messages, attachments as
   bubbles with their file name, staff messages on the right with a tick. No error toast, no
   empty thread.
3. At most N + 2: the 24h-window check that `GET .../ticket` already did before this lane
   (main's `respond_messaging_service.get_window_state`, cached 45 s, attempted once per open,
   refused offline) plus at most one background delta read. Not a call per message.
4. Same number as step 3: the panel polls `/conversation` and that makes 0 Respond.io attempts.
5. Older stored messages load (`/conversation/page?before=...`). The counter grows by 0 while the
   scroll stays inside stored history, and by at most 1 for a scroll past the oldest stored
   message.
6. The panel fills the 375 px width with no sideways scroll. The thread and composer are usable.
7. The portal thread renders immediately from stored history.
8. At most 1 more than step 5 (the portal open's delta read). The 60 seconds of polling add 0.
9. At most M + 2 (window check plus one delta read), and those calls now succeed.
10. Same number as step 9: polling adds 0 calls.
11. The sent message appears in the panel within a second (the CRM's own mirror row in
    `chat_histories`), with a sent tick.
12. The message appears in the panel and the portal thread within seconds (n8n or the Respond.io
    webhook), and in any case within 5 minutes (reconcile). Polling still adds 0 calls.
13. The run summary reads `{"enqueued": "<job id>", "queue": "respond_io"}` within seconds. The
    worker log line looks like `chat reconcile: {'selected': <n>, 'synced': <n>, 'errors': <n>, ...}`,
    with no crash.
14. Older history past the stored rows loads with one Respond.io read per page. Once Respond.io
    reports the start of the conversation, no more older pages are requested.
