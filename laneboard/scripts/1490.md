# Hand test #1490 (ATTACH-GROUNDING-TYPO)

Prod 5 Oct 2026 12:02: "m495 techincal drawings" got a product answer instead of the technical
drawing file. This build keeps a misspelt document word ONLY when the parser read it as a
document type and at least one word the customer typed is exactly a word of that type
("drawings" is a word of "technical drawing"). A document word misspelt on its own ("phtos")
is NOT rescued: that is the case the open grounding decision (b), trust the parser outright,
would change. This test shows both, so the owner can decide (b) on real replies.

## URL
crew test copy

## Setup

1. Sign in to the crew test copy as a superadmin.
2. Pick a test contact whose access agent is General Enquiries and who may see product attachments. Check: any ask from it in the chatbot console has the trace line `Access allowed for General Enquiries`.
3. Pick product P: one product that has at least one Technical Drawing file AND at least one Product Photos file on its Files tab. Use M495 if it has both; otherwise any product that has both. Write down P's product code, its product name, and the file names under Technical Drawing and under Product Photos.
4. Every step below starts a NEW conversation in the chatbot console for this contact, so no earlier turn carries over.

## Steps

1. Open the chatbot console. As the test contact, send `<P code> techincal drawings` (for M495: `m495 techincal drawings`).
2. Read the reply and the turn trace (`grounding` entry, `parse._parser_raw`, the tool called).
3. New conversation. Send `<P code> technical drawings` (control, correct spelling).
4. Read the reply and the tool called.
5. New conversation. Send `<P code> phtos`.
6. Read the reply and the tool called.
7. New conversation. Send `<P code> photos` (control, correct spelling).
8. Read the reply.

## Expected

1. Step 2, reply text (one numbered block per Technical Drawing file P has, these fields in this order, values from Setup 3), with the drawing file(s) attached to the message:
   ```
   I have attached the file(s) below.

   1. *Product Code:* <P code>
   *Product Name:* <P name>
   *Attachment Type:* Technical Drawing
   *File Name:* <drawing file name>
   ```
   Trace: tool `crm_master_product_attachments_list`; domain `product_attachment`; the `grounding` entry reads `kept: parser canonical_code` for raw `techincal drawings`; `parse._parser_raw.entities` holds `raw: "techincal drawings", hint: "attachment_type", canonical_code: "technical drawing"`. No product list, no "Which kind of file do you need?".
2. Step 4: exactly the same reply text and the same attached file(s) as step 2. Tool `crm_master_product_attachments_list`. The trace has no `grounding` change for the document word.
3. Step 6: NOT a file answer (this build does not rescue a typo that shares no whole word with the type). Tool `crm_master_products_list`, domain `master_products`, and the reply is P's product details, with no `Attachment Type` line and no file attached; the `grounding` entry shows `phtos` said back as a word nothing matched. This is the same as before this PR.
4. Step 8: the step 2 reply shape with `*Attachment Type:* Product Photos` and P's photo file name(s), photo(s) attached.
