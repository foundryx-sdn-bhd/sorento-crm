   (298 taps with Technical Specifications on 6 Oct; the counts below follow the copy).

   `technical drawing` -> Technical Specifications (it did on 6 Oct; turn 1 needs it) and a
   picture word -> Product Photos (`photo`, `pic`, `picture`; the resolver places the parser's
   document word through the `attachment_types` name or this set).
3. The dealer contact of the 6 Oct 22:40 test: General Enquiries access, may see product
   attachments (the trace shows `Access allowed for General Enquiries`), `chatbot_allowed`.
4. **The "pic" step (step 8) needs the parser prompt example lines.** On the owner's copy the
   production prompt (v58) drops the document entity on "they got pic/" / "pic", so the code
   can only re-list the carried type. Crew publishes the lane's example lines as an UNLABELLED
   `chatbot_semantic_parser` version on the shared dev DB (the two replacement examples under
   the SPECIFICATION addendum's "domain word alone" rule, the text in the PR's crew-done;
   `chatbot_prompt_vars.publish_wording_edit`, as #1513's v64 was published) and names the
   version number `<N>`; no label moves. Then, in the Chatbot Console
   (System Management > Chatbot Console), open the `Prompt version` picker (it reads
   `Live (production label)` until a version is chosen) and select `v<N>` (the entry reads
   `v<N> · <base>`; it is the highest number in the list). Every reply bubble then shows
   `v<N>` as the prompt version it ran. Leave the picker on `v<N>` for the whole test; the
   count case (step 9) runs the same way. Without this step, step 8's rows read
   `Technical Specifications` again (the carried type re-listed over the listed page): the
   code half is right, the parser half is not.
5. Each numbered case below starts a NEW conversation in the Chatbot Console.

2. Read the reply: the header line and the brand breakdown lines.
3. Send `sorento`.
4. Read the reply: the header line and the `Attachment Type` line of every row; note the first
   three product codes listed.
5. Send `they got pic/`.
6. Read the reply and the trace (chat history > the turn's trace): which products the
   attachments tool was called with, if it was called at all.
7. Send `pic`.
8. Read the reply: every row's `Product Code` and `Attachment Type` lines, and the trace's
   `crm_master_product_attachments_list` arguments.
9. Start a new conversation. Send `which tap has technical drawing`, then `sorento`, then
   `another 10`.
10. Read the reply: the header line and the rows.

## Expected

1. (step 2) `Here's what you want: taps with technical specifications (<N>)` and one line per
   brand (Sorento, Mocha, No Logo, Cabana ...), as on 6 Oct. No "as a document type".
2. (step 4) `Here's what you want: Sorento taps with technical specifications (<M>, showing 1
   to 50)`; EVERY row `*Attachment Type:* Technical Specifications`; the trace's tool call
   carries `attachment_type_ids` = the Technical Specifications id, the same id as step 2's
   call.
3. (step 6) Whatever the parser makes of `they got pic/`: the reply never names
   `SRTWT5906-COLD TAP` or `SRTWT5906-COLD TAP-NL`, and if the tool was called its
   `product_ids` are the 50 codes listed in step 4 (no other). With `v<N>` selected the reply
   is the photos of those 50 (every row `*Attachment Type:* Product Photos`); on the
   production prompt a re-list of the Technical Specifications rows, or a clarifying ask
   (`Please provide the attachment type for ...`), is the accepted fallback.
4. (step 8) The tool is called with `product_ids` = exactly the 50 codes listed in step 4
   (none other, no COLD TAP pair) and `attachment_type_ids` = the Product Photos id; every row
   `*Attachment Type:* Product Photos`; every `Product Code` on the rows is a code from step 4.
   No `Technical Specifications` row.
5. (step 10) `Here's what you want: Sorento taps with technical specifications (<M>, showing
   51 to <K>)` (the `showing` figures state what the tool rendered) and every row
   `*Attachment Type:* Technical Specifications`: the page continues after the listed rows
   settled onto the focus.
6. No uuid anywhere in any reply. No wording changed from the 6 Oct copy. The reply bubbles in
   the console show `v<N>` for the whole run.
