# Hand test: PR #1623 AC-CANCEL-CRM (AutoCount Cancel SO derives cancelled qty)

## URL

crew test copy

## Setup

The owner runs no commands. Every command below, and API steps 2, 6 and 7, are run by crew; the
owner only looks at screens before and after each crew step.

- `$URL` is the test copy (http://ac-cancel-crm.localhost:3104).
- `KEY=$(cat state/handtest/crew-handtest-1356.key)`: the crew hand-test key (ESB user). Not the
  backend `EXTERNAL_API_KEY`, which resolves to the n8n integration and lacks the order slugs. The
  ESB user's role needs `scm.sales_orders.edit` (gives `scm.cancel_sales_orders.view` / `.edit`)
  and `scm.sales_orders.delete` (gives `scm.cancel_sales_orders.delete`, used by step 7).
- `$DATABASE_URL` is the copy's database (read only below).

1. The combined `crew-migration` from the PR is applied (both tables, `qty_cancelled`,
   `cancelled_by_cancel_doc`, the 12 `scm.cancel_*` / `scm.consignment*` slugs).
2. SO373923's CB110, CB110-R and CB110LP must read as AutoCount sends them: ordered 36,
   TransferedQty 36, `closed`. Crew confirmed this on the copy (13 Oct). If they ever drift, re-push
   the SO through the ingest endpoint, never by editing rows. The read endpoint returns each line's
   `product_ref`, and the ingest matches products by `product_code`, so the codes come from the DB:
   - `REF=$(psql "$DATABASE_URL" -Atc "SELECT r.source_ref FROM integration_references r JOIN sales_orders s ON s.id::text = r.entity_id WHERE r.entity_type = 'sales_orders' AND s.so_number = 'SO373923'")`
   - `curl -s -X POST "$URL/api/v1/external/read/sales_orders" -H "X-API-Key: $KEY" -H "Content-Type: application/json" -d "{\"companyCode\":\"SRT\",\"source_refs\":[\"$REF\"]}" > so373923.json`
   - `psql "$DATABASE_URL" -Atc "SELECT json_object_agg(l.source_ref, p.product_code) FROM sales_order_lines l JOIN sales_orders s ON s.id = l.sales_order_id JOIN products p ON p.id = l.product_id WHERE s.so_number = 'SO373923'" > codes.json` (each line's code, keyed by the line `source_ref` the read returns)
   - `jq --slurpfile codes codes.json '{companyCode:"SRT", records:[.records[0] | .lines |= map(.product_code = $codes[0][.source_ref] | if (.product_code|IN("CB110","CB110-R","CB110LP")) then .qty_delivered = 36 else . end)]}' so373923.json > so373923-push.json`
   - `curl -s -X POST "$URL/api/v1/external/ingest/sales_orders" -H "X-API-Key: $KEY" -H "Content-Type: application/json" -d @so373923-push.json`
   - Check: `psql "$DATABASE_URL" -c "SELECT p.product_code, l.qty_ordered, l.qty_delivered, l.line_status FROM sales_order_lines l JOIN sales_orders s ON s.id = l.sales_order_id JOIN products p ON p.id = l.product_id WHERE s.so_number = 'SO373923' AND p.product_code IN ('CB110','CB110-R','CB110LP')"` reads 36 / 36 / closed for all three.
3. The fake Cancel SO below is `ZZXS-HAND-1`, DocKey 990001: it names the SO, the item and the
   line's own location but no line key, as every 2026 XS line does. Each of the three items is one
   line on SO373923, so the exact single-line match runs (a group is SO + item + location, compared
   exactly). Crew builds its lines from the SO itself, so each carries that line's location:
   - `psql "$DATABASE_URL" -Atc "SELECT json_agg(json_build_object('DtlKey', 991000 + n, 'Seq', n, 'ItemCode', code, 'Location', loc, 'Qty', 36, 'FromDocType', 'SO', 'FromDocNo', 'SO373923', 'FromDocDtlKey', 0) ORDER BY n) FROM (SELECT p.product_code AS code, w.warehouse_code AS loc, row_number() OVER (ORDER BY p.product_code) AS n FROM sales_order_lines l JOIN sales_orders s ON s.id = l.sales_order_id JOIN products p ON p.id = l.product_id LEFT JOIN warehouses w ON w.id = l.warehouse_id WHERE s.so_number = 'SO373923' AND p.product_code IN ('CB110','CB110-R','CB110LP')) x" > xs-details.json`
   - Check: `jq length xs-details.json` reads 3 (one line per item; anything else, stop and tell the
     lane).
   - `jq '{companyCode:"SRT", book:"db1", records:[{DocKey:990001, DocNo:"ZZXS-HAND-1", DocDate:"2026-10-13", Cancelled:"F", LastModified:"2026-10-13T10:00:00", Details:.}]}' xs-details.json > xs-push.json`

## Steps

1. Owner: sign in. From the sidebar open the fulfilment planning board and find SO373923. Note
   CB110, CB110-R and CB110LP listed with Planned 36 each, and that Confirm refuses them
   ("components add up to 0 and the line is open for 36").
2. Crew runs: `curl -s -X POST "$URL/api/v1/external/ingest/cancel_sales_orders" -H "X-API-Key: $KEY" -H "Content-Type: application/json" -d @xs-push.json` and tells the owner the response.
3. Owner: reload the board and find SO373923 again.
4. Owner: confirm the order's remaining lines on the board as usual.
5. Owner: from the sidebar open Sales Orders, open SO373923, then the Lines tab.
6. Crew runs the same `curl` as step 2, unchanged, and tells the owner the response.
7. Crew runs: `curl -s -X POST "$URL/api/v1/external/ingest/cancel_sales_orders/deletions" -H "X-API-Key: $KEY" -H "Content-Type: application/json" -d '{"companyCode":"SRT","book":"db1","doc_date_from":"2026-10-13","doc_date_to":"2026-10-13","doc_keys":[990001]}'` and tells the owner the response.
8. Owner: reload the SO373923 Lines tab, then the board.
